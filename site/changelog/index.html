What it forgot to tell you.

Everything that changed, newest first. The contract is frozen at version 1, so new features arrive as optional fields: a request that does not use them runs exactly as before.

v1.2.0

latest release 2026-10-28

Two RFCs. One default behavior change: a run that hits a step or tool-call limit now ends with an answer. Everything else is opt-in, through new optional fields.

changed · SPEC §10.1 · RFC 0002

A run never ends on a limit without an answer

When the model spent the last allowed step on tool calls, the run used to end stopped_limit with nothing to show the user. Now the last step goes without tools and with a short engine note: answer with what you have. If the model answers, the run is completed with limit_reached. If it does not, the run ends with a fixed localized fallback and answer_source: "fallback". The same holds for max_tool_calls. limits.final_answer: false restores the old behavior.

Added

  • Journal on disk. LOG_DIR writes the event journal to daily JSONL files that survive a deploy, keeps a week by default and caps the directory size. GET /logs reads memory first and falls back to disk, and reports source. The system prompt is stored once by hash instead of in every run.
  • One presentation per run. Mark the tools and fenced blocks your UI renders with presents, and set limits.max_presentations. Once the budget is spent, presenting tools are hidden and refused, and presenting blocks are cut.
  • Blocks belong to the final answer. With interim: "drop", a block written in a tool step is removed from the history, so the model stops copying a half-finished card step after step.
  • Grounded values. grounded checks that values in a block came from results of the tools you name. An invented value goes through the normal repair.
  • Repeat tolerance. limits.max_repeated_calls sets how many repeated calls are forgiven before tools are disabled; 0 cuts on the first.

v1.1.2

2026-10-27

Fixes from an external audit. No breaking contract changes: SPEC §6.5 now spells out the cancelled deferred call, and the harness gets one new obligation, H21.

Fixed

  • Cancel with a deferred call in the batch. If a write tool had already answered deferred while a parallel read was still running, cancel left that call open, and the next run with the history was refused with unresolved_tool_call. Any terminal status other than awaiting_tool now closes it with cancelled, and its tool_calls[] entry keeps the operation_id. The harness then cancels the operation (H21).
  • Cancel during an image download. The aborted download surfaced as image_fetch_failed, and the run ended failed. It now ends cancelled.
  • Repeats and max_tool_calls. A repeated call could end the run stopped_limit. Repeats are not executed and no longer count toward the limit. The model gets repeated_call and continues.
  • Token estimates. Without provider usage the output estimate now counts generated tool calls. The prompt estimate behind trimming and max_total_tokens counts the per-message date lines.

Security

  • Callback diagnostics. A receiver that echoed the request in its error body could leak CALLBACK_SECRET, a callback.headers value or a query value into last_error, the journal and stdout. These values are now redacted wherever they occur.

Example harness

  • A new amount for the same order updates the pending operation and bumps its version, so a card for the old amount can no longer be confirmed. A callback that beats the POST /runs response is no longer lost. An operation that is already closed continues the conversation at once. H21 is implemented.

v1.1.1

2026-10-27

Fixes and security updates. No contract changes.

  • Signed Claude thinking after the engine's own edits. Newer Claude models bind each thinking block to the exact prefix before it, so replaying a block after trimming was a 400. On those steps the engine asks the provider to drop the stale blocks, and the run goes on. Drops are journaled as thinking_blocks_dropped.
  • Claude context window: 1M. The built-in profile assumed 200k for every Claude model and trimmed histories five times too early. It is now 1M, and 200k only for the models that have it.
  • Dependencies. hono, @hono/node-server, undici 7.30.1 and fast-uri updated for known advisories. The engine moved to Zod 4, because Zod 3 could exhaust memory on a large invalid body before the request was refused.

v1.1.0

2026-10-27
new · SPEC §6.8 · RFC 0001

Skills and deferred tools

The model no longer has to see every tool and every instruction from the first step. A request can carry skills[] in the SKILL.md shape, and tools marked defer_loading. The model sees a one-line index of skills, calls load_skill when the conversation needs one, and gets its instructions plus its tools from the next step.

The engine still remembers nothing: what is loaded comes back from the history on every run. On Anthropic models the activated tools arrive inside the conversation, so the prompt cache survives.

"skills": [
  { "name": "order-returns",
    "description": "Return and refund policy. Use when the user asks about a return.",
    "body": "# Returns\n\nCheck the order status first ...",
    "tools": ["createReturn"] }
]

Added

  • skills[] and the built-in load_skill. An index of skills (name and description, sorted) is appended to the system prompt. Loading a skill returns its body and makes the tools it lists callable from the next step. Built-in calls take a step but do not count toward max_tool_calls.
  • Deferred tools. tools[].defer_loading: true keeps a tool out of the context until something activates it. A call to a tool that is not loaded yet gets tool_not_loaded: it is not executed, not counted and not treated as a repeat, so the same call works on the next step.
  • The built-in search_tools. For deferred tools that belong to no skill: BM25 over tool names, descriptions and argument names. It is the same code on every provider and is reproducible from the request. Matches inside a skill point the model to load_skill, so a tool arrives together with its instructions.
  • Cache-friendly activation. On Anthropic models with tool search every tool is declared on every step with defer_loading, and activation is a tool_reference in the conversation, so the cached prefix never changes. Other providers get the new tool on the next step, at the cost of one prefix cache miss.
  • Stateless restoration. Loaded skills and found tools come back from the tool messages the engine marks builtin: true; the harness stores them like any other message. Trimming never drops a turn that keeps a tool loaded.
  • Observability. Built-in calls appear in tool_calls[] with builtin: true. New journal events: skill_loaded, skill_unknown, skills_restored, tool_search, builtin_history_invalid. Text the model wrote, like a search query, goes only to the journal's content.
  • An example harness. examples/sqlite-harness: history, a read tool, a write tool with approval, continuation and recovery on SQLite, with a chat in the terminal.

Changed

  • Vercel AI SDK 6. The engine moved to ai 6.0, @ai-sdk/anthropic 3.0 and @ai-sdk/openai-compatible 2.0. Billing still records uncached input separately from cache read and cache write. On tool_choice: none steps Anthropic now keeps the tools declared.
  • Checked live. The signed-thinking round trip across two runs, a tool call with thinking, images, and a skill loaded mid-run on the Anthropic API. The second turn of that run reads its prefix from the cache.
  • README. A banner, badges, a comparison with neighbouring tools, a quickstart with the published Docker image, and a CHANGELOG.md.

v1.0.0

2026-10-15

The first public release: the agent loop as a stateless HTTP service, with the v1 contract frozen.

  • The contract. One POST /runs is one run, with everything in the request. SSE with replay, synchronous cancel, at-least-once callback with recovery through GET /runs/{id}, and a session lock held until the result is acknowledged.
  • The loop. Driven step by step: tools run only after the model's step is complete, and limits are checked at step boundaries. It detects repeated calls and empty results, and repairs malformed fenced blocks in the answer.
  • Write intents. A tool with effect: write answers deferred with an operation id; approval and execution live in your system.
  • Usage. One record per provider attempt, including failed and interrupted ones, with cache tokens, optional cost and estimated budgets.
  • Providers. Anthropic, OpenAI, DeepSeek, GLM, GigaChat, MiniMax and any OpenAI-compatible endpoint, with a per-key queue and AIMD rate limiting.
  • Operations. Controlled egress, provider proxies, graceful shutdown, an error webhook, an in-memory event journal, and engine text in English and Russian.
